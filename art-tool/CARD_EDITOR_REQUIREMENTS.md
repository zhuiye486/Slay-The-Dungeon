# 全局卡牌编辑工具需求对齐

## 1. 目标

将现有的卡牌美术工具升级为全局性的卡牌编辑工具，使开发者可以在同一个网页界面中快速修改卡牌数值和属性，立即看到卡牌预览，并在确认后将修改应用回主项目。

第一阶段优先解决：

- 快速修改卡牌数值
- 修改后的实时卡牌预览
- 修改内容进入暂存区，确认后再提交到主项目

## 2. 范围

### 本阶段支持

- 只编辑卡牌
- 直接读取现有 Java 卡牌源码
- 直接修改现有 Java 卡牌源码
- 复用现有卡牌列表、详情弹窗、图片裁剪、套框预览、暂存区和提交流程
- 主要支持英文卡牌信息，同时保留中文名称编辑能力

### 本阶段不支持

- 角色、遗物、技能、事件等其他游戏对象
- CSV/JSON 批量导入导出
- 批量修改多张卡牌
- 独立的数据文件作为卡牌数据源

## 3. 可编辑字段

每张卡牌需要在现有详情界面中提供可编辑控件，字段包括：

| 字段 | 说明 |
| --- | --- |
| 英文名称 | 卡牌在 Java 源码和英文显示中的名称 |
| 中文名称 | 卡牌中文显示名称 |
| 描述 | 卡牌效果描述，支持升级前后的效果表达 |
| 费用 | 卡牌能量费用 |
| 稀有度 | 卡牌稀有度；需求中重复提及，界面只保留一个字段 |
| 类型 | Attack、Skill、Power 等卡牌类型 |
| 伤害 | 卡牌伤害数值 |
| 格挡 | 卡牌格挡数值 |
| 魔法数字 | 卡牌使用的通用数值或源码中的 magic number |
| 治疗 | 卡牌治疗数值 |
| 升级效果 | 升级后费用、数值、描述或其他效果变化 |
| 标签 | 用于筛选、检索或标识卡牌的标签 |
| 卡图 | PNG 卡牌图片，沿用现有图片暂存和裁剪流程 |

字段应尽量映射到现有 Java 卡牌类中的真实字段、构造参数、描述文本和升级逻辑。无法可靠识别的源码结构不能静默覆盖，应显示警告并要求确认。

## 4. 交互流程

### 4.1 浏览和编辑

1. 工具扫描主项目中的 Java 卡牌源码。
2. 卡牌列表继续显示现有的名称、职业、类型、效果、图片和暂存状态。
3. 点击卡牌打开现有详情界面。
4. 在详情界面直接编辑字段，不新增独立的编辑页面。
5. 字段修改后立即更新本地编辑状态和卡牌预览。

### 4.2 暂存

1. 用户修改任意卡牌字段或替换卡图后，卡牌进入暂存状态。
2. 暂存内容写入现有 `art-tool/staging/`，不立即修改主项目源码。
3. 暂存清单需要同时记录：
   - 卡牌 ID
   - 修改前值
   - 修改后值
   - 修改字段
   - 卡图和裁剪信息
   - 校验警告
   - 暂存时间
4. 重新打开卡牌时，应优先显示暂存后的内容和预览。
5. 用户可以撤销当前卡牌的暂存修改，恢复到主项目中的原始值。

### 4.3 预览

- 数值、描述、类型、费用和升级效果修改后，卡牌预览实时更新。
- 卡图继续使用现有裁剪框和 mask 套框预览。
- 预览应能体现至少以下状态：
  - 当前卡牌信息
  - 卡图
  - 费用
  - 类型
  - 稀有度
  - 描述
  - 升级前后效果
- 预览使用暂存值，而不是直接重新读取未修改的 Java 源码。

### 4.4 提交

1. 用户点击现有“提交到主项目”。
2. 提交确认窗口列出所有待提交卡牌及字段变更。
3. 提交前再次执行字段校验和源码写入预检查。
4. 确认后，将暂存字段修改应用到对应 Java 文件。
5. 卡图继续按现有规则生成 `500×380` 和 `250×190` PNG，并更新 `IMG_PATH`。
6. 提交成功后清理对应暂存项，并重新扫描或刷新卡牌数据。
7. 提交失败时保留暂存内容，并显示具体文件、字段和错误原因。

## 5. 校验要求

校验分为编辑时提示和提交前阻止两类。

### 编辑时提示

- 必填字段为空
- 数值字段不是有效数字
- 数值超出合理范围
- 类型、稀有度等枚举值不受支持
- 描述或名称与当前源码结构无法匹配
- 卡图格式、尺寸或透明度存在问题

### 提交前阻止

- 卡牌 ID 或 Java 文件无法定位
- 解析到的 Java 结构与预期不一致
- 必须写入的字段无法安全替换
- 费用、伤害、格挡、魔法数字或治疗等数值非法
- 名称导致类名、资源名或路径冲突
- 卡图不是可处理的 PNG

所有警告和错误都应关联到具体卡牌和具体字段，不能只显示笼统的失败信息。

## 6. 数据和文件约定

- Java 源码是唯一的正式数据来源。
- 工具启动或重新扫描时，从 Java 源码解析卡牌数据。
- 暂存数据只保存编辑中的差异和必要的预览数据。
- 暂存文件应保持 JSON 格式，便于 Git 查看、比较和恢复。
- 不改变现有卡牌 Java 类的公共结构，除非某个字段确实需要新增。
- 源码写入应尽量保留原有格式和未编辑内容。
- 写入前应创建可恢复的原始内容或使用暂存差异，避免部分写入造成卡牌文件损坏。

## 7. 撤销、恢复和版本控制

需要支持：

- 当前字段编辑的撤销和恢复
- 当前卡牌恢复到上次扫描状态
- 暂存修改的撤销
- 提交前查看修改前后对比
- Git 友好的 JSON 暂存记录和 Java 最小化修改

第一阶段可以先按“当前卡牌级别”实现撤销与恢复，不要求完整的跨卡牌编辑历史。

## 8. UI 调整原则

- 保留现有卡牌网格、筛选、详情弹窗、图片编辑区和暂存区。
- 在现有“卡牌信息”和“效果描述”区域内增加编辑控件。
- 只读字段与可编辑字段要有清晰的视觉区分。
- 数值字段优先使用紧凑的数字输入框。
- 类型、稀有度等固定选项使用下拉框或选择控件。
- 标签使用可增删的标签输入控件。
- 编辑状态、校验状态和暂存状态需要在卡牌列表及详情页中可见。
- 预览区不因字段编辑而消失或跳转，方便快速调整数值。

## 9. 第一阶段验收标准

- 能从现有 Java 源码扫描并展示卡牌的核心字段。
- 可以在现有详情界面编辑上述字段。
- 修改费用、伤害、格挡、魔法数字、治疗或升级效果后，预览立即变化。
- 修改后的内容可以进入暂存区，并在刷新页面后恢复显示。
- 可以查看修改前后差异并撤销暂存修改。
- 非法数值或无法安全解析的源码会被明确提示，且不能提交。
- 确认提交后，修改能正确写回对应 Java 文件。
- 卡图编辑仍按现有暂存、裁剪、套框预览和提交规则工作。
- 提交失败时不会丢失暂存内容。
- 英文卡牌编辑流程完整可用，中文名称可以单独编辑和保存。

## 10. 待后续确认的实现细节

以下内容不影响当前需求方向，但在开始编码前需要根据现有卡牌源码进一步确认：

- 英文名称和中文名称分别存储在哪些 Java 或 localization 文件中。
- “魔法数字”是映射到固定字段、构造参数，还是允许一张卡牌编辑多个数值。
- 标签是否写入 Java 源码，还是只作为工具侧管理元数据。
- 升级效果是否拆分为独立字段，还是从升级方法和描述中共同解析。
- 一张卡牌存在多个数值时，界面如何标识每个数值的用途。
- 是否需要支持卡牌描述中的动态变量和关键词编辑。
